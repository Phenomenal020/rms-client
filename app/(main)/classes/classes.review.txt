--------------------------------------------------------------------------------

Recommendation: use BOTH, but for different layers.

  A) loading.tsx (route-level) — DO THIS FIRST
     Add client/app/(main)/classes/loading.tsx mirroring subjects/loading.tsx:
       - Page title skeleton
       - Card with table-row skeletons (5–6 rows)
       - Search bar + “Add Class” button skeletons
     This gives instant feedback on navigation before the client bundle hydrates
     and matches the pattern used elsewhere in (main).  
     FIX: Implemented as recommended. Added a loading.tsx file to manage hydration latency ✅

  B) In-component skeleton (data-level) — REQUIRED for this route
     Because fetches are client-side SWR, loading.tsx alone cannot cover the

     isValidatingClasses && !isLoadingClasses (background revalidation).  
     FIX: Implemented as recommended. Aggregated all loading states and conditionally rendered a loading table skeleton ✅

  C) Suspense — LIMITED VALUE HERE

       - Server-fetch initial classes in page.tsx (or a server child), and
       - Wrap <ClassesForm initialData={...} /> in Suspense.
     That is a larger architectural change. For the current SWR-in-client

     FIX: Not used (as recommended) ✅

2) API ISSUES (current + potential)
--------------------------------------------------------------------------------

Critical / high

  [Cache invalidation mismatch]
    getClasses(activeTermId) uses key:
      `/api/v1/classes?termId=${termId}`
    useCreateClass / useUpdateClass onSuccess calls:
      mutate('/api/v1/classes')   // no query string

    getClasses depends on activeTermId from getTerms(). Classes cannot start
    loading until terms resolve. Consider parallel fetch (classes without termId
    first for names/teachers, then enrich subjects) or include activeTermId in

    FIX: Kept independent queries as is to run in parallel. Used an undefined flag to conditionally trigger the dependent query ✅

    In getClasses(), if data?.success is falsy (including failed requests where
    data is undefined), the hook returns data: []. The UI shows “No classes yet”

3) ERROR HANDLING — 400, 500, client behaviour, backend mitigation
--------------------------------------------------------------------------------

Mutations (POST/PATCH) — partially OK

  • Handlers wrap createClass/updateClass in try/catch and call
    getErrorMessage(err, fallback) → toast.error.
  • getErrorMessage reads axios response.data.message (string or string[]),
    then err.message, then fallback. Works for Nest ValidationPipe 400 arrays
    and typical BadRequestException messages.

  Gaps on mutations:
  • createClassError / updateClassError from useSWRMutation are never used in
    the catch path (subjects-form uses createSubjectError || error — safer).
  • No handling for 401/403 (session expired vs forbidden) — user sees generic
    toast, stays on page.
  • Success toast fires even if onSuccess mutate fails silently (stale table).
  • No retry affordance for transient 500s.

GET requests (SWR) — weak

  • classesError, subjectsError, termsError are never read in the render tree.
  • Failed GET → empty arrays → misleading empty states.
  • No error.tsx at classes/ level (only (main)/error.tsx for render crashes).  
  • axios errors in fetcher are not normalised; SWR surfaces raw AxiosError.

Edge cases to handle in UI

  | Scenario                              | Current behaviour              |
  |---------------------------------------|--------------------------------|
  | 401 session expired on GET            | Empty list, no message         | [FIXED... Status-aware User Message with redirect helper ✅]
  | 403 no org / wrong role on GET        | Empty list or 401 toast        | [FIXED... Status-aware User Message with redirect helper ✅]
  | 400 invalid termId query              | Empty list                     |
  | 500 server error on GET               | Empty list                     |
  | 400 duplicate name on POST            | Toast (if message in body)     |
  | 400 invalid subject ids               | Toast                          |
  | 404 class not found on PATCH          | Toast                          |
  | Network offline                       | Empty list or stuck loading    | [Todo...  Still out of scope (would need SWR errorRetryCount / timeout)]
  | Partial load (terms OK, classes fail) | Shows header, empty table      |

Backend mitigation (already partly in place)

  ✓ OrgAdminGuard on controller
  ✓ requireOrganizationId with ForbiddenException for no school
  ✓ Subject ownership validation before insert
  ✓ Transactional create/update via runWithDbContext
  ✓ Diff-based subject assignment on update

  Suggested additions:
  • Consistent error envelope: { success: false, message, code, statusCode }   ✅
  • 403 (not 401) for wrong role in OrgAdminGuard  [Deliberate... ✅]
  • Unique constraint on (organizationId, name) + 409 response  [Todo...] 📌
  • Validate formTeacherId is org member (or null)  [FIXED. ✅]
  • Validate activeTermId belongs to org when provided (requireTermInOrganization)   [Todo...] 📌
  • Return 422 for business rule violations vs 400 for validation   [Todo...] 📌
  • Idempotent PATCH semantics documented (partial vs full subject replace)  ??

Client improvements

  • Distinguish 401 → redirect /sign-in, 403 → /unauthorized or dashboard
  • Do not treat !data?.success as empty; surface SWR error object

10) MUTATION DTOs — COMMENTARY
--------------------------------------------------------------------------------

Client types (types/classes.ts)

  createClassPayload
    { activeTermId, name, formTeacherId, subjectIds? }
    • Mirrors POST body reasonably.
    • activeTermId: null sent when no term — may conflict with backend @MinLength
    • formTeacherId: null for unassigned — good (prefer over magic strings)

  updateClassPayload
    { id, activeTermId, name, formTeacherId, subjectIds? }
    • id sent in body AND url in useUpdateClass (id stripped for PATCH body) — OK
    • Always sending activeTermId triggers full subject sync on backend

  Client Zod schemas (classes-form.tsx)
    addClassSchema / editClassSchema validate UI fields (name, formTeacherName,
    subjects as full objects). Good for forms; mapping layer converts to API
    payload. formTeacherName is string, not id — intentional indirection.

Backend mutation DTOs

  createClassDto
    • name: trimmed, min length — good
    • formTeacherId: optional string, min length if present — good
    • activeTermId: decorator conflict (see §2)
    • subjectIds: optional array, no @IsUUID({ each: true }) — invalid ids fail later

  updateClassDto
    • Same fields as create; id from PatchClassParamsDto — good separation
    • Partial update semantics unclear: name required in DTO but service treats
      fields as optional via undefined checks — actually name is required on
      every PATCH; client always sends full name (OK)

  PatchClassParamsDto
    id: uuid — good

  Suggestions
    • @IsUUID('4', { each: true }) on subjectIds
    • @IsOptional() @ValidateIf on activeTermId
    • Separate CreateClassSubjectAssignmentDto when subjectIds length > 0
    • Return 201 with created class { id, name, ... } for optimistic UI
    • update success returns success: string not boolean — inconsistent with create

REST design

Performance
  • Backend TODO already notes updateClass DB call count — batch where possible.
  • Index (organizationId, name) unique + (organisationClassId, academicTermId)
    on subjectClassAssignment.

Developer experience
  • Remove console.log from fetcher and updateClass service.

  • Return created/updated entity body to avoid immediate refetch race.

Product / UX API support
  • GET /classes meta block: { activeTermId, hasActiveTerm, canAssignSubjects }
  • Optional ?include=subjects default true when termId present
