1) LOADING INDICATION — Suspense vs loading.js (with skeletons)
--------------------------------------------------------------------------------

Current state
  • page.tsx is "use client" with manual isLoading checks → <ResultsSkeleton />.
  • ResultsComponent also returns <ResultsSkeleton /> while grading, assessment,
    teacher-classes, or class-record loads — two skeleton phases in sequence.
  • ResultsSkeleton exists and mirrors the final layout well (header, student
    picker, school block, stats grid, table, signatures). Good foundation.
  • No loading.tsx in students-view/ (unlike subjects, classes, teachers).
  • No error.tsx — errors are inline <p className="text-destructive">.
  • getUserWithRelations() is called in page.tsx but isUserLoading gates skeleton;
    user data is never used in page.tsx (dead fetch).
  • SWR isValidating is not used — no subtle “refreshing” affordance during
    background revalidation after save (save-scores onSuccess does not invalidate).

Recommendation: use BOTH layers (same pattern as subjects/classes).

  A) loading.tsx (route-level) + ResultsSkeleton fallback
     On first navigation, Next shows loading.tsx immediately before client
     bundle hydrates — avoids blank flash. Export default:

       export default function Loading() {
         return <ResultsSkeleton />;
       } ✅

  B) In-component skeleton (data-level) — partially done ✅
     page.tsx: isUserLoading || isTermsLoading → ResultsSkeleton
     ResultsComponent: isGradingLoading || isAssessmentLoading || modeLoading
     → ResultsSkeleton

     Improvement: use staged skeletons or partial UI instead of full-page
     skeleton twice. Example: after term/school resolve, show shell + skeleton
     only for the table block while class record loads.

  C) Suspense — not recommended today ✅
     All data fetching is client SWR hooks. Suspense only helps if you refactor
     to Server Components + async fetch + suspense boundaries. Not worth the
     churn for this route unless you migrate the whole (main) shell.

  D) Mutation loading — partial ✅
     • resultTable: isPending + Loader2 on Save ✅
     • printExportHeader: isExporting disables Export ✅
     • AcceptRejectButtons: no loading state on Accept/Submit — double-click
       risk during accept/reject 📌
     • useSaveStudentScores isMutating not wired to Save button 📌

  E) Empty-state vs loading confusion
     getTerms / getGradingSystem / getAssessmentStructure return data: [] when
     data?.success is falsy (including failed requests). Can flash
     "No academic term" or render with empty grading before real error surfaces. ✅

3) ERROR HANDLING — 400, 500, client behaviour, backend mitigation
--------------------------------------------------------------------------------

Current state
  • page.tsx: userError || termsError → plain red text, no retry.
  • ResultsComponent: gradingError || assessmentError → same pattern.
  • Mutations: try/catch + toast.error + getErrorMessage (not getApiErrorMessage).
  • No handleAuthRedirect on mutations (subjects/teachers pattern absent).
  • No ErrorBanner, no error.tsx, no throw to error boundary (TODO in page).
  • Fetcher (axios) throws on non-2xx → SWR populates error — but queries
    still return empty data arrays when success flag missing.

  | Scenario                              | Current client behaviour              |
  |---------------------------------------|---------------------------------------|
  | GET terms 401 (teacher)               | Often "No academic term available"    |
  | GET grading 401 (teacher)             | Empty grading → "N/A" grades          |
  | GET class-record 403/404              | "No students available"               |
  | save-scores 400 validation            | Toast with API message (OK)           |
  | save-scores 401 (orgadmin)            | Generic toast; no redirect            |
  | export 400 pending duplicate          | Toast (if message propagated)         |
  | export / accept / reject 500          | Generic fallback toast                |
  | Network offline                       | SWR error.message; no retry UI        |

400 handling (mutations)
  • Backend student-view.service throws explicit BadRequestException messages
    (inactive term, invalid structure id, not enrolled, pending export exists).
  • Client handleSaveScores checks academicTerm.status !== "ACTIVE" before API —
    good UX duplicate of server requireActive.
  • resultTable zod validates structure length and non-negative ints; does not
    cap score at assessment percentage weight.
  • Reject modal: disabled Submit when reason blank; server RejectRecordDto
    @MinLength(1) @MaxLength(200) — client should mirror max length 📌

500 handling
  • student-view service: no runWithDbContext on getTeacherClasses,
    getClassRecord, saveStudentScores (unlike assessment-structure GET).
    Raw DB errors may leak or map inconsistently via all-exceptions.filter.
  • Client shows getErrorMessage fallback — acceptable if message is generic.

Recommended client fixes (mirror subjects/teachers)
  📌 getApiErrorMessage + handleAuthRedirect in handleSaveScores, handleExport,
     handleAccept, handleReject ✅
  📌 ErrorBanner + mutate retry for load errors (terms, grading, class record) ✅
  📌 useEffect on fetch errors: 401/403 → redirect sign-in or dashboard ✅
  📌 error.tsx route boundary for uncaught errors (optional) ✅
  📌 Distinguish 400 toast (validation) vs 500 toast (retry suggestion)

Backend mitigation
  • Align guards so the role that uses the page can call all required GETs. ✅
  • runWithDbContext on student-view read/write methods for consistent 500 mapping.
  • Return 403 Forbidden (not 401) when role wrong but session valid — helps
    client messaging (getApiErrorMessage already maps 403).
  • Embed { gradingSystem, assessmentStructure } in class-record response to
    reduce round-trips and avoid guard split (optional API design). 📌


4) DISABLE ACTIONS FOR ORGADMIN (only regular users edit) ✅
--------------------------------------------------------------------------------

Intent: role "user" = form teacher can edit scores + export; role "orgadmin"
should not mutate on this route (they use dashboard/review for approve/reject).

Current state
  • No role check anywhere in students-view folder.
  • ResultTable has readOnly prop — used only for mode === "review" (org admin
    reviewing a snapshot), not for orgadmin on /students-view.
  • Backend already enforces: UserGuard on student-view mutations; orgadmin gets
    401 if they bypass UI.

Recommended pattern (inverse of subjects canManage)

  In page.tsx or ResultsComponent:

    import { useUser } from "@/contexts/user-context";
    // or: const { user } = getUserWithRelations();

    const canEdit = user?.role === "user";
    const isOrgAdmin = user?.role === "orgadmin";

  Pass down:
    • <ResultTable readOnly={!canEdit || mode === "review"} … />
    • <PrintExportHeader disabled={!canEdit || isGlobalEditing || isExporting} />
      — add explicit canEdit prop or fold into disabled
    • <StudentSelection isGlobalEditing={isGlobalEditing || !canEdit} />
    • Guard handlers:
        if (!canEdit) return;  // at top of startEditingScores, handleSaveScores,
                               // handleExport

  UX options for orgadmin on /students-view
    A) Read-only view (show data if you add org-readable GET endpoints) 📌
    B) Redirect to /dashboard with toast "Form teachers only" 📌
    C) Hide sidebar link for orgadmin (they have review queue on dashboard) 📌

  Do NOT use OrgAdminGate (that blocks non-orgadmin). You need a TeacherGate or
  simple canEdit flag. Optional shared component:

    // shared-components/teacher-gate.tsx
    if (user?.role !== "user") return fallback; // or redirect

  Accept/reject buttons: only in mode="review" on dashboard — already separate
  from /students-view; keep OrgAdminGuard on record PATCH endpoints.

  P0 — Guard / access model
    • Introduce read endpoints (or guard variant) for term summary, grading
      system, and assessment structure accessible to any org member with
      requireTermInOrganization — keep writes orgadmin-only.
    • OR single GET student-view/report-context?termId= returning {
        term, gradingSystem, assessmentStructure, classes? } for teachers.

  P1 — student-view module
    • Wrap getTeacherClasses, getClassRecord, saveStudentScores,
      saveClassRecordExport in runWithDbContext for consistent 500 handling.

    • getClassRecord: optional ?studentId= to reduce payload when paginating.

    • getRecord: return metadata + content (status, reviewedAt) for UI badges.
    • accept/reject: return 409 if already terminal state.
    • Filter pending requests by status PENDING for orgadmin dashboard.

  P3 — Client / API contract
    • Standardise { success, data, message } — queries should not swallow errors.
    • Shared OpenAPI or zod schemas generated from Nest DTOs for client forms.
    • Remove console.log from useSaveStudentScores.

  P4 — Performance
    • class-record can be large; consider student pagination or lazy load scores.
    • ETag / If-None-Match on class-record for repeat visits.

  P5 — Security
    • UserGuard returns 401 for wrong role — prefer 403 when authenticated.
    • Never accept full class snapshot from client on export (already correct).
    • Rate-limit save-scores to prevent accidental bulk spam.
