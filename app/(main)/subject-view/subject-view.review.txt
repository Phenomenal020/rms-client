9) GET REQUEST DTOs (backend + client query params)
--------------------------------------------------------------------------------

  Subject-view has NO dedicated GET routes. All reads go through:

  GET /api/v1/terms
    • Guard: OrgMemberGuard on GET ✅
    • Client: getTerms()

  GET /api/v1/grading-system?termId=
    • DTO: GetGradingSystemQueryDto { termId: UUID }
    • Guard: OrgMemberGuard on GET ✅
    • Client: getGradingSystem(academicTerm.id)

  GET /api/v1/assessment-structure?termId=
    • DTO: GetAssessmentStructureDto { termId: UUID }
    • Guard: OrgMemberGuard on GET ✅
    • Client: getAssessmentStructure(academicTerm.id)

  GET /api/v1/student-view/classes?termId=
    • DTO: GetTeacherClassesQueryDto { termId: UUID }
    • Guard: OrgMemberGuard on GET ✅
    • Client: getTeacherClasses(academicTerm.id, true)

  GET /api/v1/student-view/class-record?classId=&termId=
    • DTO: GetClassRecordQueryDto { classId, termId }
    • Guard: OrgMemberGuard on GET ✅
    • Response: assignments[], students[] (SubjectRowDto, StudentResultDto)
    • Client: getClassRecord(firstClassId, academicTerm.id, true)
    • Subject-view derives subjectOptions from assignments (subjectId + name) ✅

  Recommended future GET (if subject-teacher model added)
    📌 GET /subject-view/my-subjects?termId=
    📌 GET /subject-view/subject-record?subjectId=&classId=&termId=

  Client query anti-pattern (shared)
    if (!data?.success) return { data: [] | null } — masks HTTP errors. 📌
